# 《流放之路1》攻略项目 AGENTS 规则重构设计

## 1. 目标

将现有 `AGENTS.md` 从累积式注意事项重构为《流放之路1》（Path of Exile 1）BD攻略与策略攻略项目的统一执行入口，并以专项规范承载详细流程。

新规则体系必须：

- 仅处理《流放之路1》，禁止混入《流放之路2》资料；
- 同时覆盖新手、有基础玩家和终局玩家；
- 每份正式攻略按“最低可执行方案 → 稳定方案 → 高投入方案”分层；
- 覆盖BD、剧情开荒、舆图推进、虚空石、收藏地图槽、T16/T17、祭坛、圣甲虫、赛季机制、首领轮转、挑战、装备采购、交易搜索、做装和止损；
- 国服与国际服并列处理版本、市场、赛季时间、交易和可获取性差异；
- 采用分层证据制度，而不是机械要求所有事实同时由PoE Wiki和PoEDB证明；
- 把纠错记录中的系统性问题转化为可执行规则和后续自动验证契约；
- 保护用户现有文件和未提交改动。

纯市场套利、囤货和倒卖不属于项目范围。市场数据可以用于比较采购、制作与策略成本，但不得把投机作为攻略主体。

## 2. 总体架构

采用“分层式单入口”结构。根目录 `AGENTS.md` 是唯一强制入口，包含不可跳过的硬规则、风险分级、任务路由、停止条件、归档触发条件和交付门槛。详细方法拆入 `项目规范/`。

```text
流放之路/
├─ AGENTS.md
├─ 项目规范/
│  ├─ 证据来源与术语.md
│  ├─ BD分析与归档.md
│  ├─ 策略攻略与收益.md
│  ├─ 装备交易与制作.md
│  ├─ 剧情宝石与工作簿.md
│  ├─ 版本管理与纠错.md
│  └─ 交付前检查表.md
├─ BD档案/
├─ 策略档案/
├─ BD知识库.md
├─ 纠错记录.md
├─ outputs/
└─ docs/
   └─ superpowers/
      ├─ specs/
      └─ plans/
```

### 2.1 根入口硬规则

`AGENTS.md` 必须独立包含：

1. 项目只处理《流放之路1》。
2. 所有结论标注版本和服务器。
3. 按答错成本进行风险分级。
4. 使用分层证据制度。
5. 证据不足时交付已确认部分，高成本或不可逆操作局部停止。
6. 国服术语使用可搜索的简体中文原文。
7. 普通问答不自动落盘，重大研究按触发条件归档。
8. 用户纠错必须进入纠错闭环。
9. 专项任务必须读取对应规范。
10. 正式交付前必须执行对应检查表。

### 2.2 任务路由

| 任务 | 必须读取 |
|---|---|
| 普通机制问答 | 证据来源与术语 |
| PoB、BD推荐或升级 | 证据来源与术语＋BD分析与归档 |
| T16/T17、祭坛、甲虫、赛季机制 | 证据来源与术语＋策略攻略与收益 |
| 买装备、交易搜索、做装 | 证据来源与术语＋装备交易与制作 |
| 剧情开荒、宝石取得、Excel路线 | 证据来源与术语＋剧情宝石与工作簿 |
| 新版本迁移或用户纠错 | 版本管理与纠错＋受影响领域规范 |
| 最终交付 | 交付前检查表＋受影响领域规范 |

跨领域任务必须加载所有受影响规范。例如“为当前PoB设计T17策略并给装备升级”同时加载BD、策略和装备规范。

## 3. 证据制度与风险分级

### 3.1 来源职责

| 来源 | 主要职责 |
|---|---|
| GGG官方公告、补丁说明、论坛公告 | 版本变化、发布日期、官方规则和已知问题 |
| 游戏客户端、官方静态数据 | 当前实际文本、物品属性和可见行为 |
| PoE Wiki | 机制解释、规则、任务、版本历史和英文原名 |
| PoEDB简体中文站 | 简体中文名称、词缀、数值、权重、标签、需求和任务矩阵 |
| Path of Building Community | 指定角色的计算、配置、装备、天赋、技能和伤害构成 |
| 官方交易站、货币交换市场 | 当前挂单、搜索字段、供给和价格区间 |
| poe.ninja | 国际服市场趋势和公开角色样本，不代表完整市场 |
| 社区攻略与视频 | 作者路线、操作经验、实测样本和观点 |
| 用户截图、录像和实测 | 当前客户端状态及指定条件下的直接证据 |

社区资料可以作为证据，但必须记录作者、发布日期、版本、服务器和样本量，并分离作者观点、实测观察与已验证机制。

### 3.2 证据状态

重要结论按以下状态管理：

- 已确认：目标版本和服务器下有直接证据，并完成必要交叉核验；
- 条件成立：只在列明配置、版本、服务器或操作条件下成立；
- 作者声明：来源作者给出的数据，尚未独立复现；
- 实测观察：有样本和环境记录，但不能推导为普遍规律；
- 推断：由已知事实推导，必须展示依据；
- 未确认：证据不足或来源冲突；
- 历史：只适用于旧版本或旧赛季。

最终攻略不要求逐句贴标签，但关键机制、成本、收益、可获取性和切换条件必须体现证据状态。

### 3.3 来源冲突

1. 当前游戏客户端或可复现行为优先于数据库旧页面。
2. 当前官方补丁说明优先于尚未同步的百科。
3. 当前国服客户端是国服显示文本的最高依据，PoEDB简中页是默认数据库。
4. 机制以当前官方说明和PoE Wiki为主，PoEDB用于底层数据交叉检查。
5. PoB只证明指定导入和配置下的计算，不能覆盖游戏实际机制。
6. 市场结论必须来自目标服务器的当前数据，不能跨服迁移。
7. 无法判定冲突时保留差异，不擅自选择有利结论。

### 3.4 风险分级

- 低风险：术语解释、基础机制和不导致投入的普通问答。可快速回答，但仍需标注版本；不稳定事实必须查询。
- 中风险：BD搭配、天赋、技能连接、普通刷图路线和挑战步骤。必须读取专项规范，核对版本和关键前置。
- 高风险：做装、批量采购、洗点、昂贵替换、T17高投入策略、跨BD伤害比较、赛季限定物品和市场收益。必须完整核验，提供替代、失败分支与止损。

### 3.5 停止条件

以下情况不得继续给出确定性高风险操作：

- 目标服务器或版本不明确；
- 高额投入依赖的关键机制尚未确认；
- 做装底材、物品等级、词缀标签或权重无法核对；
- PoB比较条件无法统一；
- 当前赛季可获取性没有可靠证据；
- 交易搜索未在目标服务器验证；
- 操作可能破坏装备或角色，但没有恢复路径。

代理仍可交付已确认部分、保守替代方案和验证步骤。

## 4. BD与PoB工作流

### 4.1 四类数据分离

必须区分：

1. 用户当前角色快照；
2. 目标成型PoB；
3. 攻略作者声明的数据；
4. 代理在统一配置下重新计算的数据。

每次收到新PoB，记录来源、角色等级、导入日期，以及代码长度、附件哈希或其他可区分标识。禁止复用历史附件解释当前角色。

### 4.2 PoB最低检查项

- 游戏版本和天赋树版本；
- 职业、升华和等级；
- 主技能及变体、等级、品质、连接与启用状态；
- 实际触发技能和触发频率；
- 光环、诅咒、防御、位移与触发组；
- 装备、药剂、天赋、专精、普通珠宝和星团珠宝；
- Config中的敌人、近期条件、充能球、异常状态、凋零和曝露；
- Full DPS的技能、召唤物或图腾数量；
- PoB是否自动选择错误触发技能；
- 自定义词缀和不可持续条件。

### 4.3 比较与升级

跨BD或升级比较必须统一敌人类型、技能阶段、数量口径、触发频率、可持续减益、充能球、近期条件、药剂和爆发覆盖率、防御环境。无法统一时只能做结构性比较，禁止确定倍率结论。

升级建议必须说明改动、解决的问题、伤害/生存/手感/资源收益、前置条件、冲突、预算、替代、可逆性和验证方法。

### 4.4 BD档案结构

正式BD档案至少包含：

1. 版本、服务器与来源；
2. 适用水平和玩法定位；
3. 当前快照与目标状态；
4. 核心技能和伤害闭环；
5. 防御与恢复闭环；
6. 资源与保留闭环；
7. 最低可执行方案；
8. 稳定方案；
9. 高投入方案；
10. 剧情到终局阶段路线；
11. 各阶段技能组和取得时间；
12. 天赋、升华、专精和珠宝顺序；
13. 装备、关键词缀与替代品；
14. 地图禁忌、首领弱点和操作循环；
15. 升级优先级、切换条件和止损；
16. 短板、证据边界和待验证事项；
17. 重要版本变化。

一个BD使用一个主档案。用户补充同一BD时更新主档案并保留重要快照；核心技能、升华或机制改变时视为新BD；对比样本必须明确标记。

## 5. 策略攻略与收益

### 5.1 策略范围

覆盖剧情、舆图、虚空石、收藏地图槽、T16/T17、灭界者/焚界者/贤主与祭坛、圣甲虫和碎片、赛季机制、首领轮转、挑战成就、装备采购与制作。

### 5.2 三层方案

- 最低可执行：必要解锁、最低角色能力与投入、替代品、失败成本和撤退条件；
- 稳定：推荐投入、完成率、安全词缀、稳定补给和长期操作；
- 高投入：理论上限、额外难度、角色要求、高价消耗品止损和边际收益。

### 5.3 理论最优与角色适配

策略先解释机制理论最优，再判断角色实际可执行性。有PoB时检查清图、单体、最大承伤、恢复、地图词缀、祭坛负面、死亡影响及必要换装。无PoB时列出能力门槛、危险词缀和最低测试方法，不得默认用户能完成。

每个投入项必须说明它影响区域数量、怪群、特定奖励、地图/通货/圣甲虫更多倍率、祭坛、首领专属掉落或周转速度中的哪一项，禁止混用不同奖励。

### 5.4 收益标准

给出收益时记录版本、服务器、赛季、日期、策略、样本地图数、全部投入、耗时、原始掉落、易售与难售产出、挂单或成交价格、交易时间、死亡失败和净收益区间。

小样本只能称观察值。没有样本或只有作者口述时，只分析收益结构，不宣称稳定时薪。

### 5.5 策略档案

文件命名：`<版本>-<服务器或双服>-<内容>-<目标>.md`。

档案至少包含目标、版本服务器、前置、机制、理论最优、三层方案、地图/甲虫/碎片/天赋、操作顺序、角色门槛、收益样本、失败止损、双服差异和证据边界。

## 6. 装备、交易与做装

装备建议先定义BD快照、目标问题、不可破坏机制、必要/可选词缀、属性与孔色需求、预算和联动换装。不能只按面板DPS推荐。

交易搜索区分精确物品、手工词缀、PoB权重、批量消耗品、国服和国际服。PoB权重请求必须使用PoB计算的有效权重，不能用少量人工词缀代替。

交付搜索链接前验证服务器、赛季、类别、槽位、价格单位、数量、权重内容、链接加载和国服实际显示文本。

双服市场分别查询，记录时间、搜索条件、样本、最低价、可成交价格带、批量价、深度与流动性。挂单价不称成交价。未经明确授权，不登录、联系、下单或购买。

做装路线必须核验底材、物品等级、影响、词缀类别/标签/等级/权重、工艺条件、前后缀空间、元工艺、不可逆操作、版本可用性和双服材料成本。

路线必须包含准备、步骤目的、成功判定、可接受半成品、失败回收、不可逆节点、单步停止、总止损、成品购买对比、替代品和升级顺序。

## 7. 剧情、宝石与工作簿

PoB阶段技能组不能直接作为取得清单。每颗宝石独立核验中英文名、等级、章节、任务、NPC、职业领取/购买、互斥奖励、萨欧赛、莉莉、特殊来源和最早稳定取得阶段。

阶段路线记录主连接、辅助、光环、诅咒、防御、位移、触发、首领工具、练级宝石、切换条件和装备/颜色条件。技能不得早于取得阶段启用。互斥奖励明确选择，其余列为商店补购。批量采购必须逐颗通过验证。

剧情路线还包含必做/可跳过任务、天赋点、试炼、抗性惩罚、装备检查、技能和防御切换、异界前检查，以及白黄红图、虚空石和收藏地图槽目标。区分快速与新手稳定路线。

只有用户要求逐步路线、采购、阶段对比或可筛选数据时才生成Excel。工作簿至少包含总览、逐步路线、技能阶段、宝石取得、装备、天赋升华、舆图、采购、验证结果和来源。

导出前验证宝石覆盖、职业权限、使用时点、互斥奖励、路线连续性、统一数据一致性、版本服务器、当前事实源及视觉布局。

## 8. 归档触发与知识流

- 普通即时问答不落盘；
- 新BD或重大更新必须更新 `BD档案/`；
- 完整通货、舆图、挑战或首领策略必须更新 `策略档案/`；
- 跨多个BD或策略仍成立的稳定结论才摘要到 `BD知识库.md`；
- Excel只在用户要求逐步路线、采购或数据对比时生成；
- 交易链接、正则、PoB和原始数据只有实际使用并验证后才保存；
- 重要版本变化、纠错和可复用研究强制归档。

知识晋升路径：

```text
即时回答
  ↓ 经核验且可复用
BD档案或策略档案
  ↓ 跨多个案例仍成立
BD知识库
  ↓ 发现错误或版本失效
纠错记录／历史档案
```

一次截图、小样本收益或单个作者观点不得直接晋升为通用规则。

## 9. 版本管理与纠错

正式产物记录游戏、版本、赛季、服务器、创建日期、核验日期、来源版本和状态（当前、部分兼容、待复核、历史）。页面存在不代表当前赛季可获取。

数值微调、少量连接、优先级和证据补充原地更新。核心技能、职业升华、闭环、来源或策略核心改变时新建版本档案。旧档案保留历史价值，在文件开头链接替代版本；旧价格和收益不得沿用于当前赛季。

用户纠错、新证据、档案冲突、版本更新、验证失败或系统性复制错误必须触发纠错闭环：暂停旧结论、读取同类记录、重新核验、明确正误、定位根因、全项目搜索、更新受影响产物、记录纠错、重跑检查并说明残余不确定性。

纠错记录必须包含错误说法、正确结论、原因、影响范围、修复、来源和防复发规则或自动检查。

## 10. 交付前检查与失败处理

通用检查：

- 游戏、版本、赛季、服务器和日期完整；
- 专有名词采用 `中文（English）`，国服搜索文本为实际原文；
- 事实、作者声明、实测、推断和未知分离；
- 没有继承旧价格、旧掉落或旧获取结论；
- 来源指向具体页面，冲突已披露；
- 高成本建议有替代、失败分支和止损；
- 适用水平和三层方案明确；
- 文件、PoB、交易链接和正则可用；
- 没有占位符、残留待办或内部临时说明。

专项检查：

- BD：四类数据分离、触发与数量正确、Config统一、闭环完整、阶段合法、快照不混淆；
- 策略：理论与可执行分离、投入与奖励对应、前置和操作完整、收益样本齐全；
- 装备市场：底材词缀核验、链接服务器正确、挂单成交分开、失败回收与止损完整；
- 剧情工作簿：宝石覆盖、职业权限、互斥与时点正确，数据一致，视觉检查通过。

验证失败时不得声称完成。先列出失败项和影响，修复可修复问题并重验；外部资料缺失时交付已确认部分；高风险核心无法确认时停止相关建议。不得因时间、篇幅或成本压力跳过强制检查。

## 11. 用户文件保护

- 修改前检查Git状态和目标文件差异；
- 未提交内容默认属于用户；
- 不覆盖、回退或删除不相关改动；
- 临时数据和正式档案分离；
- 多个候选档案先确定主档案再合并；
- 批量迁移保留来源和恢复路径。

## 12. 实施边界

本次规则重构阶段负责：

1. 重构根 `AGENTS.md`；
2. 创建七份专项规范；
3. 创建 `策略档案/`；
4. 保留并迁移现有有效规则；
5. 将纠错经验转化为通用防错规则；
6. 在规则中定义人工检查和后续自动验证契约。

本次不实现完整自动验证脚本。验证器作为后续独立实施阶段；现有工作簿脚本只在相关任务中按新契约升级。

实施前必须检查当前 `AGENTS.md` 的未提交差异，逐条判断保留、迁移或合并，不得直接覆盖。

## 13. 验收标准

设计实施完成后，应满足：

- 根 `AGENTS.md` 能独立说明项目边界、硬规则、任务路由、停止条件和交付门槛；
- 每类任务都能映射到明确的专项规范；
- 现有有效规则没有丢失；
- BD与策略拥有不同但一致的归档工作流；
- 双服、分层证据、风险分级和三层方案成为强制要求；
- 纠错记录中的已知错误类型都有对应防复发规则；
- 规则不存在互相矛盾、不可验证或要求无限研究的条款；
- 所有新增Markdown链接和目录路径有效；
- 未改动或提交用户其他未提交文件。
